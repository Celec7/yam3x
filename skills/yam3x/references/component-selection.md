# Component selection

Choose by intent first, then check the component's documented variants and composition rules. Do not choose by visual similarity or by the name of a component in another design system.

## Variants and local extensions

- Start with the component and variant documented on its page.
- If the product needs a local variant, make it a deliberate extension: keep the component's states, semantics, and accessibility, and document the difference.
- Some components are YAM3X-specific compositions; use their page for usage and describe them as YAM3X components.

Use the [component catalog](https://yam3x.iscccc.cc/components/) to browse the current set. Run the CLI list to see the components available to install.

For new designs, prefer connected button groups over the legacy segmented button and a navigation bar or rail over the legacy navigation drawer. Those legacy components remain available for maintenance.

## Breakpoint swaps

| Need                 | Compact                      | Medium / Expanded             | Large / Extra-large                   |
| -------------------- | ---------------------------- | ----------------------------- | ------------------------------------- |
| Navigation           | Navigation bar               | Collapsed navigation rail     | Expanded or collapsed navigation rail |
| Supplemental actions | Bottom sheet                 | Menu                          | Menu                                  |
| Communication        | Simple or full-screen dialog | Basic dialog                  | Basic dialog                          |
| Pane count           | 1                            | 1 (2 for low-density content) | 2 recommended; 3 with a side sheet    |

Your app may choose its own breakpoint values; the official breakpoints explain the intent behind the swaps.

Only swap components that are functionally equivalent. Do not swap a button for a chip, a menu for an action, or a list for a card merely because the layout is wider.

## Composition rules

- One primary constructive action per screen. Do not add a FAB for a secondary action.
- Use a native link for navigation; use a button for an action.
- Use the shared Form Field anatomy for forms rather than a private field surface.
- Use the shared menu and option geometry for dropdowns and suggestions.
- Keep critical information in the primary content flow, not only in a tooltip.
- Keep a keyboard and click path for every gesture.
- Start from a documented variant. If none fits, build a local extension from the component's primitives and document how it differs.
